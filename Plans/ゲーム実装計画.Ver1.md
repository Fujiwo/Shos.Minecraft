# ゲーム実装計画書

参照文書: `Specifications/ゲーム仕様書.Ver1.md`、`Specifications/詳細システム設計書.Ver1.md`

---

## 第1章:実装方針

- 本計画は、1つのステップを「実装 → 動作確認 → 次のステップへ着手」の順で完了させてから次のステップに進めるステップバイステップ方式とする。複数のステップを並行して着手することはしない。
- すべてのゲームロジック、画面、API、永続化は、単一の ASP.NET Core MVC プロジェクトで構成する。HTML/CSS は `Views/` と `wwwroot` に配置し、`Controller` から画面と API を管理する。
- 実装対象は、依存先のステップが完了済みであり、未解決の確認事項がない最も小さい番号のステップから選ぶ。未確定事項が残る場合は、実装を止めて仕様確認へ戻る。
- 各ステップの完了時点で、単一プロジェクトとしてビルド・起動できる状態を保つ。あるステップの成果物が、次のステップの未実装部分へ依存してビルドできなくなることは許容しない。
- 実装を実行するごとに `Plans/実装進捗.Ver1.md` を更新する(存在しない場合は新規作成する)。着手・完了したステップ、実施内容、動作確認結果、未解決事項を都度記録する。

### 1.1 実装対象のアーキテクチャ

- ルート: `Sources/Shos.Minecraft/`
- 画面: `Controllers/`、`Views/`
- データ契約: `Models/`
- 静的資産: `wwwroot/css/`、`wwwroot/js/`、`wwwroot/images/`
- 永続化: `Data/`、`DbContext`、`EF Core`
- API: `GameApiController` などの `Controller` を同一プロジェクト内で定義する

## 第3章:各ステップの詳細

### ステップ0: 補助作業: 単一プロジェクト雛形構築
- 現状: `Sources/Shos.Minecraft/` には既定の ASP.NET Core MVC テンプレート(`Program.cs`、`Controllers/HomeController.cs`(Index/Privacy/Error)、既定の `Views/`、`wwwroot/css`・`wwwroot/js`・`wwwroot/lib`)のみが存在し、ゲーム固有のコード・APIはまだ追加されていない。
- 作業項目:
  - `Sources/Shos.Minecraft/Program.cs` に API 用のルーティングを追加する
  - `Sources/Shos.Minecraft/Controllers/` に `GameApiController` を新規追加する(既存の `HomeController` は維持する)
  - `Sources/Shos.Minecraft/Models/` にゲーム用の DTO と ViewModel を追加する
  - `Sources/Shos.Minecraft/Views/` と `Sources/Shos.Minecraft/wwwroot/` にゲーム画面用の資産を追加する
- 完了条件:
  - アプリ起動時にブラウザからホーム画面が取得できること
  - `/api` 系のルートが利用可能であること
- 依存関係: なし

### ステップ1: Razor View と CSS/TypeScript の基盤
- 作業項目:
  - `Views/Home/Index.cshtml` に canvas と UI の骨格を配置する
  - `Views/Shared/_Layout.cshtml` に共有レイアウトを定義する
  - `wwwroot/css/site.css` で画面全体のレイアウトを整える
  - `wwwroot/js/game.ts` で起動処理を実装し、`Microsoft.TypeScript.MSBuild` によりコンパイルされた `game.js` を `Views` から読み込む
- 完了条件:
  - ブラウザで白紙または空のゲーム画面が表示されること
  - TypeScript(コンパイル後の JavaScript)が `canvas` と画面を正しく初期化すること
- 依存関係: ステップ0の完了が前提

### ステップ2: ブロックとチャンクの基盤
- 作業項目:
  - `wwwroot/js/world/BlockTypes.ts` にブロック定義を置く
  - `wwwroot/js/world/Chunk.ts` に `Uint8Array` ベースのチャンク管理を実装する
  - 16×256×16 のインデックス計算を維持する
- 完了条件:
  - 指定座標に値を設定した後に同じ値を読み出せること
  - 空気と水の非衝突扱いが実装されていること
- 依存関係: ステップ1の完了が前提

### ステップ3: 描画とメッシュ生成
- 作業項目:
  - `wwwroot/js/world/ChunkMeshBuilder.ts` に不可視面カリングを実装し、`positions` / `normals` / `uvs` (`Float32Array`) と `indices` (`Uint32Array`) を生成する(詳細システム設計書 2.2 のメッシュデータ形式に準拠)。
  - `wwwroot/js/world/ChunkMeshWorker.ts` として Web Worker を分離し、チャンクの `blocks: Uint8Array` を受け取ってメッシュ生成結果を `Transferable` な `ArrayBuffer` として返す。
  - UVは各面に単位UV座標((0,0), (1,0), (1,1), (0,1))を割り当てるロジックのみとし、ブロックID別のアトラスオフセット算出、実際のテクスチャアトラス画像・Babylon.jsへの投入と描画は本ステップの対象外とする(後続ステップで対応)。
- 完了条件:
  - 1チャンクの外周面だけが描画対象として生成されること
  - 内側の面がカリングされていること
- 依存関係: ステップ2の完了が前提

### ステップ4: 地形生成とワールド取得
- 作業項目:
  - `Terrain/` などのサーバー側ロジックでパーリンノイズを生成する
  - `GameApiController` でチャンク取得 API を提供する
  - `Views` 側の JS が取得したチャンクを描画に反映する
- 完了条件:
  - 同一シード値で同一地形が再現できること
  - API からチャンクデータを取得し、画面に反映できること
- 依存関係: ステップ3の完了が前提

### ステップ5: プレイヤー移動と衝突
- 作業項目:
  - `wwwroot/js/player/` 配下でカメラ、入力、重力、ジャンプ、衝突を実装する
  - `Controllers` 側の API と連携して状態更新を行う
- 完了条件:
  - WASD で移動し、Space でジャンプし、地面で静止すること
  - 水ブロックには通常衝突判定が効かないこと
- 依存関係: ステップ2、ステップ3の完了が前提

### ステップ6: ブロック破壊・設置とインベントリ
- 作業項目:
  - `wwwroot/js/interaction/` にレイキャスト、破壊、設置を実装する
  - `Models/` と `Controllers/` にインベントリ状態を保持する DTO を定義する
- 完了条件:
  - ブロックを長押しして破壊できること
  - ホットバーのブロックを右クリックで設置できること
  - インベントリの表示と選択が切り替わること
- 依存関係: ステップ4、ステップ5の完了が前提

### ステップ7: 体力・落下ダメージ・回復
- 作業項目:
  - `Model` と `Controller` を用いて player state を管理する
  - HUD を `Views` 側で表示し、JS が更新する
- 完了条件:
  - 体力が HUD に表示されること
  - 高所落下でダメージが発生し、自然回復や復活が働くこと
- 依存関係: ステップ5、ステップ6の完了が前提

### ステップ8: 永続化とセーブ
- 作業項目:
  - `Data/` 配下で `World` / `Chunk` / `InventoryItem` を定義する
  - `PUT /api/worlds/{id}/state` で状態と変更済みチャンクを一括保存する
  - `GET /api/worlds/{id}/chunks` で再ロードする
- 完了条件:
  - ワールド状態が保存され、再起動後に復元されること
  - 変更済みチャンクのみが保存対象となること
- 依存関係: ステップ4、ステップ6、ステップ7の完了が前提

### ステップ9: 検証とリファインメント
- 作業項目:
  - フレームレート、保存整合性、境界条件を確認する
  - 仕様が未確定な箇所を明示し、設計書へ反映する
- 完了条件:
  - ビルドと実行が成功し、主要なゲーム体験が確認できること
  - 未解決の仕様差分が明確になっていること
- 依存関係: ステップ8の完了が前提

## 第4章:リスクと確認事項

- 単一プロジェクトに集約すると、画面と API の責務分離が曖昧になりやすい。`Controllers` と `Views` の役割分担を明確にする。
- TypeScript のビルド(`Microsoft.TypeScript.MSBuild`)と ASP.NET Core のルーティング・静的ファイル配信の整合性を確認する。
- クライアント側の描画負荷が高くなるため、チャンク生成とメッシュ処理は Worker と分離する設計に留める。
- 保存と再読込でのデータ整合性を、1回のトランザクションでまとめて管理する。
- 仕様に不足がある項目は、実装前にユーザー確認または設計書修正を必須とする。

---

## 結論

本計画の基本方針は、画面・API・データ永続化を 1 つの ASP.NET Core MVC プロジェクトに閉じ込め、`Views/` と `wwwroot/` で HTML/CSS/TypeScript(コンパイル後のJS)を表現することにある。これにより、ゲームの機能実装を単一アプリとして管理し、依存の境界が明確なまま段階的に開発を進める。
