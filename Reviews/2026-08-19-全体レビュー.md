## 指摘事項(重大度順)

### Medium

1. **`Plans/実装進捗.Ver1.md` に記載の検証コマンド `dotnet test` が現在の SDK では実行できない**
   - ファイルパス: `Plans/実装進捗.Ver1.md`(「## 検証コマンド」節)、`Sources/Shos.Minecraft.Tests/Shos.Minecraft.Tests.csproj`
   - 内容と影響: リポジトリに含まれる .NET SDK(`dotnet --version` → `10.0.302`)でドキュメント記載の `dotnet test Sources\Shos.Minecraft.slnx` を実行すると、
     ```
     error : Testing with VSTest target is no longer supported by Microsoft.Testing.Platform on .NET 10 SDK and later.
     If you use dotnet test, you should opt-in to the new dotnet test experience.
     ```
     というエラーで即座に失敗する(テストは1件も実行されない)。`Shos.Minecraft.Tests.csproj` は Microsoft.Testing.Platform(`IsTestingPlatformApplication=true` / xunit.v3)を採用しているため、`dotnet test` の新体験への切り替え設定(例: `dotnet test` 用の `.runsettings`、あるいは `dotnet run --project` でのテストアプリ直接実行、または `DOTNET_CLI_ENABLE_LEGACY_TESTINGPLATFORM_TEST_COMMAND` 等の切替)が未整備であり、ドキュメント記載の再現手順どおりに実行すると「テストが通っている」ことを検証できない。CIやレビュアーがドキュメントを信じて `dotnet test` のみで確認すると、実際にはテストが1件も実行されないまま「成功」と誤認するリスクがある(実際には exit code が非0になるため気づける可能性はあるが、出力を流し読みすると見落としやすい)。
   - 修正案: `Plans/実装進捗.Ver1.md` の検証コマンドを、実際に動作する手順(例: ビルド後に `Sources/Shos.Minecraft.Tests/bin/Debug/net10.0/Shos.Minecraft.Tests` を直接実行する、または `dotnet test` を新テストプラットフォーム体験で使えるようプロジェクト設定を追加する)に更新する。可能であれば `dotnet test` がそのまま使えるように `.csproj`/`global.json` 側を調整することが望ましい。
   - 追加すべきテスト: 新規のプロダクトコードテストは不要だが、CI設定を追加する場合は「ドキュメント記載のコマンドで実際にテストが実行され、実行件数が期待通りであること」をCIログで確認できるようにするとよい。

### Low

2. **Babylon.js を Subresource Integrity (SRI) なしで CDN 読み込みしている**
   - ファイルパス: `Sources/Shos.Minecraft/Views/Home/Index.cshtml:11`(`<script src="https://cdn.babylonjs.com/babylon.js"></script>`)
   - 内容と影響: 詳細システム設計書 2.0 の方針(npm 非導入、CDN 経由で `BABYLON` を読み込む)自体は妥当だが、`integrity` / `crossorigin` 属性が付与されていない。CDN が侵害された場合や中間者攻撃を受けた場合、任意スクリプトが読み込まれるサプライチェーンリスクがある。MVPの単一プレイヤー用途でリスクは低いが、外部CDN依存である以上、対策の余地がある。
   - 修正案: `<script>` タグに `integrity="sha384-..."` と `crossorigin="anonymous"` を付与する(Babylon.js の配布ハッシュを固定バージョンで取得して設定する)。
   - 追加すべきテスト: 自動テストは困難なため、手動確認手順として「SRIハッシュが実際の配布物と一致することを確認する」手順を記録するのが望ましい。

3. **`GET /api/worlds/{id}/chunks` に認証・レート制限がなく、任意の座標に対して毎回フル地形生成を行う**
   - ファイルパス: `Sources/Shos.Minecraft/Controllers/GameApiController.cs:18-40`、`Sources/Shos.Minecraft/Terrain/TerrainGenerator.cs`
   - 内容と影響: 現状はシングルプレイ・ローカル利用が前提(ゲーム仕様書 第1章)のため必須ではないが、エンドポイントは認証なしで公開されており、`x`/`z` に極端な値(例: `int.MaxValue`)を指定すると `chunkX * ChunkSizeX + lx` 等の整数演算がオーバーフローしうる(未検証だが、`unchecked` な通常の `int` 演算のため例外にはならず、決定的だが無意味な地形が返るのみ)。また、リクエストごとに 16×256×16 のブロック配列生成+ Perlinノイズ(4オクターブ)+ GZip圧縮を行うため、クライアントが同一 `WorldId` に対して大量の座標をリクエストすると相応のCPU/メモリを消費する。ステップ8で `Worlds`/`Chunks` の永続化が入れば結果はキャッシュされる想定だが、現時点では都度生成のみ。
   - 修正案: 現時点では致命的ではないため必須の修正ではないが、将来的に(a) `x`/`z` の妥当な範囲チェックを追加する、(b) パブリックAPIとして公開する場合はレート制限やワールド単位のチャンク数上限を検討する、と設計書・実装計画に明記しておくとよい。
   - 追加すべきテスト: `x`/`z` に極端な値を渡した場合の応答(クラッシュしない・妥当なレスポンスを返す)を確認する境界値テストを追加すると安心材料になる。

## 重大な問題なし(仕様・設計との整合性)

以下は仕様書・設計書との突き合わせの結果、**重大な不整合は検出されなかった**項目である。

- チャンク座標計算 `index = x + z * 16 + y * 16 * 16` は `Sources/Shos.Minecraft/wwwroot/js/world/Chunk.ts`、`Sources/Shos.Minecraft/Terrain/TerrainGenerator.cs`、テストコードのすべてで一貫している。
- ブロックID/衝突可否/破壊可否/ドロップの対応表(`BlockTypes.ts`)は詳細システム設計書 2.1 の表と完全一致している(空気0〜作業台10まで)。
- 水(ID:8)の非衝突・破壊不可の扱いは `Chunk.isCollidableAt` / `BlockTypes.isCollidable` に一貫して委譲されており、`ChunkMeshBuilder.ts` の不透明判定(`isOpaque = isCollidable`)もこれと整合している。水ブロック自体がメッシュを持たない挙動は `ChunkMeshBuilderSmokeTest.js` で意図的に検証済みであり、既知の仕様(テクスチャアトラス未導入段階の暫定挙動)として実装進捗にも記録されている。
- 地形生成の海面Y(64)・地表振幅(32)・土の厚み(4)・砂/草の切り替え・水充填ロジックは、仕様書に追記された暫定値(ユーザー承認済みと明記)と `TerrainGenerator.cs` の実装が一致している。
- `PlayerPhysics.ts` の重力常時適用・ジャンプ・AABB衝突・水の非衝突は詳細システム設計書 2.3 と整合しており、`PlayerPhysicsSmokeTest.js` で地面静止・落下・水中沈下・ジャンプ・水平移動衝突が検証されている。
